# smokedet — детекция эпизодов, похожих на курение, по видео

Кейс хакатона НТУ «Сириус» × Видеофор (Гатчина, 8–10 октября 2026). Подробный план — [PLAN.md](PLAN.md).

Система **не подтверждает** факт курения и не делает выводов о личности. Она находит наблюдаемый эпизод
поведения, похожего на курение, для тревоги оператору.

## Как работает

```
видео → YOLO11-pose + ByteTrack (~10 кадр/с, уточнение позы мелких людей на кропе) + замер света у рта
      → склейка оборванных треков
      → сигнал d(t) = |кисть − рот| / размер человека   (только в зоне интереса и при высоте ≥ 72px)
      → циклы жеста: подход → пауза 0.5–5 с → отвод   (фильтры: телефон у уха, кисть ниже локтя, нет подхода)
      → верификатор YOLO-World на кропах паузы: сигарета/вейп/дым → прямой признак; бутылка/чашка/телефон → отказ
      → вспышка зажигалки: новый пересвет у рта и кисти (не вокруг человека) → прямой признак для циклов рядом
      → выдох пара: у рта после паузы светлее и бледнее, чем до жеста (человек стоит) → прямой признак цикла
      → эпизод: ≥2 цикла за 20 с ИЛИ 1 цикл + прямой признак; объединение при паузе ≤ 15 с; confidence → порог
      → predictions.csv/json, manifest.json, processing_log.csv, debug/*.json, rendered/*.mp4
```

## Установка

```bash
uv venv .venv --python 3.11 && uv pip install --python .venv/bin/python -r requirements.txt
# или: python3.11 -m venv .venv && .venv/bin/pip install -r requirements.txt
source .venv/bin/activate
```

На Windows интерпретатор — `.venv/Scripts/python.exe`. torch ставится под своё железо (команды — в начале
`requirements.txt`). Точная копия проверенного окружения (Windows, CUDA 12.6):

```bash
uv pip install --python .venv/Scripts/python.exe -r requirements.lock     --extra-index-url https://download.pytorch.org/whl/cu126 --index-strategy unsafe-best-match
```

Веса и офлайн-словарь верификатора — **до выезда на объект**, там может не быть интернета:

```bash
python tools/prepare_weights.py   # weights/: pose, YOLO-World, COCO-откат yolo11s.pt + словарь *-vocab-<хэш>.pt
```

С запечённым словарём прогону не нужен CLIP. Если поменяли списки классов верификатора — запустите скрипт снова.

## Запуск

Один клип:

```bash
python run.py --input data/clip.mp4 --camera-id cam_fountain --start-time 2026-10-09T12:00:00 \
    --roi data/roi_fountain.json --out runs/demo --render
```

Набор клипов (скрытый набор — **одна команда**):

```bash
python run.py --inputs data/hidden.csv --out runs/final
```

`--workers N` — клипы параллельно, каждый в своём процессе со своими моделями (на GPU с 6 ГБ не нужно: модели двух процессов вместе с CLIP-L занимают 5.6 ГБ, и весь набор true+false идёт 41 мин против 27.5 мин в одном процессе;
на CPU/MPS выигрыша обычно нет). По умолчанию 1.

`hidden.csv` (пути — относительно CSV; `clip_id`, `start_time`, `roi` необязательны):

```csv
video_path,camera_id,clip_id,start_time,roi
cam1_001.mp4,cam_fountain,cam1_001,2026-10-09T12:00:00,roi_fountain.json
```

Параметры без правки YAML: `--set episode.confidence_threshold=0.6 --set detector.imgsz=960`, устройство: `--device cpu|mps|0`.

Маска зоны: PNG (белое — зона) или JSON с полигонами. Нарисовать по кадру:

```bash
python tools/draw_roi.py --video data/clip.mp4 --out data/roi_fountain.json
```

Пиксельные полигоны из `draw_roi.py` хранят размер кадра (`frame_size`): на видео другого разрешения той же камеры
они масштабируются, как и PNG-маска.

## Интерфейс для показа (`ui.py`)

Повтор анализа синхронно с видео в браузере: рамки и скелеты людей, линия «кисть → рот» с расстоянием `d`,
график `d(t)` по людям с порогами, карточка правила эпизода (какие условия выполнены у выбранного человека),
лента хода анализа с причинами отказов по-русски, шкала времени с циклами и эпизодами.
По умолчанию экран показывает только то, что анализ «знает» к текущей секунде: цикл появляется после отвода руки,
эпизод — когда выполнено правило, поэтому повтор выглядит как живой анализ. «Показать всё» открывает разбор целиком.

```bash
python ui.py --inputs data/demo.csv --out runs/demo        # клипы по очереди в фоне; браузер откроется сам
python ui.py --input videos/1.mp4 --camera-id cam1 --out runs/demo --port 8765
```

Входы и `--config/--set/--device/--roi` — как у `run.py`. С тем же `--out`, что у прошлого прогона, треки берутся из
`<out>/cache` и клип готов за секунды; без кэша идёт трекинг (прогресс виден на странице). Сервер слушает только
`127.0.0.1`, страница не тянет ничего из интернета — видео не покидает машину. Видео играет сам браузер (H.264 в mp4);
другой кодек перекодируется ffmpeg в `<out>/ui/` с сохранением времени кадров. Клавиши: пробел — пуск/пауза,
←/→ — ±5 с (с Shift — ±0.1 с), N/P — следующий/предыдущий эпизод, A — «показать всё»; щелчок по человеку выбирает
его для карточки правила. Адрес `#clip=<id>&t=<сек>` открывает нужный момент.

## Мониторинг (`monitor.py`)

Рабочее место оператора: стена из 12 камер (эфир и архив), проверка загруженных видео, журнал эпизодов.

```bash
python monitor.py                                  # анализ загруженных файлов — пайплайном (нужны модели)
python monitor.py --analyzer demo --port 8765      # без моделей: эпизоды файлов генерируются и помечены «демо»
python monitor.py --analyzer realtime --enqueue videos/true videos/false   # потоковый режим на имеющихся записях
python monitor.py --retention-days 7 --archive-min 30 --out runs/monitor
```

- **Анализатор проверки видео** — `pipeline` (как `run.py`), `realtime` (потоковый режим, как `run_rt.py`: 1 Гц +
  плотная проверка, правило `realtime.rule_overrides`; задания помечены «потоковый режим») или `demo`. `--enqueue`
  ставит в очередь имеющиеся записи без загрузки через браузер: видеофайлы, папки (видео в самой папке, имя в журнале —
  «папка/файл») и CSV со списком клипов, как у `run.py`. В папку загрузок кладётся жёсткая ссылка (или копия), поэтому
  очистка по сроку хранения исходник не удаляет. ROI из CSV не используется.
- **Камеры — симуляция.** Видео объекта публиковать нельзя, поэтому потоки — сцены с людьми и позой, которые
  считает сервер (`smokedet/monitor/cameras.py`, 10 к/с). Правило — как у пайплайна: ≥ 2 цикла «рука ко рту» за 20 с
  открывают эпизод, пауза > 15 с закрывает. У каждой камеры отдельный статус: «В сети», «Нет сигнала», «Задержка»,
  «Анализируется», «Ошибка»; не «В сети» — с временем последнего кадра и причиной. Отсутствие тревог не означает
  исправность камеры: у камеры без анализа вывод «анализ недоступен», а не «без срабатываний».
- **Эфир / Архив.** Архив — кольцевой буфер последних `--archive-min` минут в памяти (при запуске готовится
  `--prefill-min` минут истории). Таймлайн с отметками эпизодов, скорость 1×/4×/16×, щелчок по отметке открывает фрагмент.
- **Проверка видео.** Загрузка файла → очередь «В очереди → Анализируется → Готово | Ошибка» → эпизоды с переходом к
  нужному месту записи. Без torch/ultralytics/cv2 пайплайн недоступен, и задание завершается ошибкой с причиной.
- **Журнал** (`<out>/journal.sqlite`). Эпизод отмечает система (`detection = auto`), решение оператора хранится
  отдельно: не проверено / подтверждено / отклонено. Система не подтверждает факт курения и не устанавливает личность.
- **Хранение.** Фрагмент — эпизод с запасом 10 с до и после — хранится `--retention-days` дней от сохранения, затем
  файл удаляется автоматически (проверка раз в 10 мин), запись журнала остаётся с датой удаления. Фрагмент камеры —
  кадры позы (JSON); кнопка «Скачать» собирает из них WebM в браузере (WebCodecs, без WebCodecs — в реальном времени).
  Фрагмент файла вырезает ffmpeg (H.264 mp4); без ffmpeg хранится исходный файл, а фрагмент — окно в нём.

Адреса: `#monitor/archive`, `#check/<задание>`, `#journal/<эпизод>`. Сервер — только `127.0.0.1`; страница берёт шрифт
Inter с Google Fonts (без сети — системный шрифт), видео и кадры никуда не отправляются.
## Потоковый режим (`run_rt.py`)

Режим для работы в реальном времени: тяжёлая поза считается не на каждом кадре, а раз в секунду на кропах людей
и плотно — только у тех, у кого рука у рта. Код — `smokedet/realtime.py`, основной конвейер (`run.py`) не меняется.

1. Раз в секунду (`realtime.sparse_fps`) — лёгкий детектор людей yolo11n (`det_imgsz` 1280, `det_conf` 0.1)
   и простой трекер по IoU и центрам рамок.
2. Поза yolo11m-pose на кропах всех людей (вход 320, батчем, FP16) → расстояние кисть→рот `d`.
3. При `d < trigger_dist` (2.0) — плотная проверка человека: 5 кадр/с, с `dense_before` (3 с) назад из кольцевого
   буфера кадров до `dense_after` (6 с) после последнего срабатывания, до `max_jobs` (12) человек сразу. Кроп
   сдвигается по скорости рамки за последнюю `motion_window` (1 с), поэтому идущего человека поза не теряет, даже
   когда детектор его пропускает. По отсчётам раз в секунду — те же `build_signal` → `detect_cycles` → правило
   эпизода, что в основном конвейере; событие выдаётся в поток (алерт), как только выполнено правило.
4. CLIP ViT-L/14@336 (как стадия `appearance` основного конвейера) по кропам «рот + кисть» в паузах циклов; кропы
   берутся из памяти, видео не перечитывается. Событие без прямого признака проходит, если лучший его цикл набрал
   `appearance.min_score` (0.5, `realtime.objects_per_event`). Если CLIP оценил не меньше `realtime.many_cycles` (5)
   циклов события, лучшая оценка должна быть не ниже `many_min_score` (10): человек много раз подносит руку ко рту,
   а сигареты не видно ни разу — питьё, касание лица. Уже выданная тревога тогда снимается (запись `withdrawn` в
   `debug/<clip>_rt.json`, колонка `alerts_withdrawn`), а подтвердившись снова, выдаётся заново. Без этой стадии —
   `--no-objects`. Тревога снимается и у задания, удалённого как второе на того же человека (причина
   `duplicate:<id>`): его события в итоги не попадают.

Правило эпизода в режиме мягче основного (`realtime.rule_overrides`, перекрывает общие секции только здесь): один
цикл, confidence ≥ 0.1, без фильтров позы, `near_enter`/`near_exit` 1.2/1.5, пауза до 8 с. При 1 кадр/с и плотной
проверке второй цикл виден реже, точки позы на кропе 320 грубее, а главное требование — не пропустить ни одного
клипа с курением.

```bash
python run_rt.py --input videos/true/1.mp4 --camera-id cam1 --out runs/rt/one      # видео или RTSP
python run_rt.py --inputs runs/rt/all.csv --out runs/rt/final                      # набор клипов, CSV как у run.py
python run_rt.py --inputs runs/rt/all.csv --out runs/rt/fast --no-objects          # без стадии 4
python tools/tune_rt.py --inputs runs/rt/all.csv --cache runs/rt/final/cache \
    --grid cycle.near_enter=1.0,1.2 --grid appearance.min_score=0,0.5,1             # перебор повтором из кэша
python tools/eval_markup.py --run runs/rt/final
```

Выход — как у `run.py` (`predictions.csv/json`, `processing_log.csv`, `debug/<clip>.json`), плюс `realtime_log.csv`
(нагрузка `load` = время обработки / длительность видео по стадиям; ≤ 1 — режим успевает за потоком) и
`debug/<clip>_rt.json` (алерты с моментом выдачи и снятия, счётчики). Отсчёты стадий 1–3 кэшируются в
`<out>/cache/<clip>_rt.pkl`; `tools/tune_rt.py` повторяет по ним те же шаги, что поток, и перебирает пороги циклов,
правила и стадии 4. Параметры стадий 1–3 (триггер, плотная проверка) входят в ключ кэша — для них нужен новый прогон.

Результат на 34 клипах (19 true, 15 false, 3935 с видео; RTX 2060 6 ГБ; оценка по `rasmetka_gt.csv`, только время):

| вариант | true с событием | TP / FP / FN | F1 | FP в false | load: среднее по клипам / худший клип |
|---|---|---|---|---|---|
| по умолчанию (со стадией 4) | 19/19 | 25 / 48 / 4 | 0.490 | 14 | 0.14 / 0.51 (клип 2, толпа) |
| `--set realtime.many_cycles=0` | 19/19 | 25 / 63 / 4 | 0.427 | 29 | то же |
| `--no-objects` | 19/19 | 25 / 85 / 4 | 0.360 | 37 | 0.08 / 0.22 |

Весь набор со стадией 4 — 442 с (основной конвейер — 1647 с). Доли `load` по стадиям (среднее): детектор 0.009,
поза 1 Гц 0.013, плотная проверка 0.045, циклы 0.007, CLIP 0.058 (худший клип 0.23). Загрузка и прогрев моделей
(~21 с) делаются один раз и в `load` не входят; два GPU-прогона одновременно искажают `load`. 13 из 48 FP — дубли
уже найденного эпизода: рамки других людей в то же время (IoU с рамкой найденного 0–0.1), а не обрывы трека, так что
склейка треков их не уберёт; курят ли соседи, по разметке без рамок не понять. Строже правило (два цикла,
`near_enter` 0.8, фильтры позы) снижает FP, но теряет 2–13 true-клипов. `many_cycles` 4 даёт F1 0.51, но снимает
события самих курящих в клипах 4 и sm_y_2 (4 цикла, CLIP 1.2 и 3.9): TP там держится только за счёт события соседа.

## Выход (`--out`)

| Файл | Содержимое |
|---|---|
| `predictions.csv` / `.json` | `camera_id, clip_id, event_id, start_sec, end_sec, confidence, label, person_track_id, peak_sec, x1, y1, x2, y2` — одна строка на событие, рамка человека в `peak_sec` в пикселях исходного кадра |
| `manifest.json` | порог, правила объединения, версия, git-коммит, веса + sha256, лицензии, промпты, оборудование, полный конфиг |
| `processing_log.csv` | длительность клипа, время по стадиям, `realtime_factor` (>1 — быстрее реального времени) |
| `debug/<clip>.json` | все циклы (включая отброшенные с причиной: `short_hold`, `long_hold`, `phone_like`, `hand_low`, `hand_above_mouth`, `face_hidden`, `no_approach`, `object:bottle`…) и события (отклонённые — с `reject_reason`, например `objects_in_100%_cycles`) — для разбора ошибок |
| `rendered/<clip>.mp4` | с `--render`: зона, рамки (зелёная — человек, жёлтая — кисть у рта, красная — событие `SMOKING-LIKE 0.82`) |
| `cache/` | треки; повторный запуск с другими порогами не пересчитывает детекцию |

## Оценка и подбор порогов

```bash
python evaluate.py --pred runs/ref/predictions.csv --gt data/ref_gt.csv \
    --durations runs/ref/processing_log.csv --out runs/ref/report
```

Протокол как в кейсе: эталон ±3 с, пересечение ≥ 1 с, IoU рамок ≥ 0.30, сопоставление один к одному
по наибольшему пересечению, предсказание на ≥ 50% в IGNORE не считается FP. Формат эталона:
`camera_id, clip_id, label (POSITIVE|NEGATIVE|IGNORE), start_sec, end_sec [, person_gt_id, peak_sec, x1, y1, x2, y2, scenario]`.
Колонка `scenario` (P01…N08) даёт разбивку FP/FN по сценариям. Если организатор выдаст свой валидатор и формат —
адаптировать `smokedet/evaluation.py::parse_items`.

Подбор — **только на эталонном наборе**:

```bash
python tune.py --inputs data/ref.csv --gt data/ref_gt.csv --out runs/tune \
    --grid episode.confidence_threshold=0.3,0.4,0.5,0.6 --grid cycle.near_enter=0.5,0.6,0.7
```

### Эталон через CVAT

Разметка `rasmetka_gt.csv` — только время отметок, без человека и рамки. Чтобы получить полный эталон,
её правят в CVAT. Детекция не перезапускается: рамки людей берутся из кэша треков любого прогона.

```bash
python tools/cvat_export.py --inputs data/ref.csv --cache runs/ref/cache --out runs/cvat   # XML на видео + labels.json
python tools/cvat_import.py runs/cvat_done --inputs data/ref.csv --cache runs/ref/cache --out data/ref_gt.csv
```

1. В CVAT (только локальный, docker: видео объекта нельзя отправлять в облако) создать проект и в Constructor → Raw
   вставить `labels.json`. Метки: `smoking` / `not_smoking` / `ignore` (эпизоды, в эталоне — POSITIVE / NEGATIVE / IGNORE)
   и `person` (треки трекера, для справки, в эталон не идут).
2. На каждое видео — задача с именем `clip_id` (frame step 1, без start/stop frame), затем Actions → Upload annotations →
   «CVAT 1.1» → `<clip_id>.xml`.
3. Эпизод — трек от подъёма руки первой отметки до опускания последней. Отметки одного человека объединены
   при паузе ≤ 15 с, человек выбран по наименьшему расстоянию кисть→рот. Сомнительные привязки отмечены
   атрибутом `check` (причина — в `note`): фильтр `attr["check"] == true`, после проверки флажок снять.
   Рамка эталона — рамка трека в `peak_sec` (атрибут, по умолчанию — затяжка средней отметки).
4. Выгрузить задачи в «CVAT for video 1.1» (без изображений) в одну папку и запустить `cvat_import.py`.
   Клип узнаётся по имени видео, задачи или файла выгрузки. Каждый видимый отрезок трека эпизода — одно событие.
   Секунды считаются по pts из того же кэша (у CCTV-файлов с переменным fps `кадр/fps` уходит до 0.7 с).
   Если число кадров в CVAT и у трекера не совпадает, скрипт предупредит.

Посмотреть разметку без CVAT — ролики с рамками эпизодов (номер человека, «проверить» при `check`), фазой текущей
отметки (подъём руки / затяжка / опускание) и шкалой отметок внизу кадра:

```bash
python tools/render_markup.py --cvat runs/cvat --gt rasmetka_gt.csv --videos videos/true videos/false --out runs/markup
```

По умолчанию — клипы с эпизодами `smoking`; `--clips 1,sm_3` — выбранные, `--all` — все, `--persons` — ещё и треки
людей. Подходит и для правленой в CVAT выгрузки (XML в одной папке; без `index.csv` видео ищется по `<source>`).

## Разметка циклов (для обучения классификатора)

```bash
python tools/export_cycles.py --inputs data/ref.csv --out data/labeling/set1   # кадры циклов + cycles.jsonl
python tools/label_server.py --data data/labeling/set1 --host 0.0.0.0 --port 8765   # веб-разметчик
```

`--rejected none|object|all` — какие отброшенные циклы выгружать (по умолчанию отброшенные по предметам: это «двойники»
сигареты, самые ценные отрицательные примеры). Разметчик: клавиши S — курит, N + 1–6 — не курит (лицо, питьё, телефон,
еда, чупа-чупс, другое), U — неясно, V — виден выдох/дым; метки пишутся в `labels.jsonl`, сводка — `/labels.csv`.
Доступ по токену из строки запуска либо по логину и паролю: `python tools/label_server.py --users users.txt --add-user alice`
(пароль спросят), затем запуск с `--users users.txt`; для интернета добавьте `--cert/--key` (HTTPS). Разметчик ничего не отправляет наружу; это записи объекта, поэтому порт держите
только во внутренней сети. Папка `data/` не коммитится.

## Скорость (Windows, RTX 2060 6 ГБ, CUDA, кадр 1920×1080, yolo11m-pose, imgsz 1280)

Трекинг одного клипа (66 с, 662 кадра анализа):

| Режим | кадр/с |
|---|---|
| FP32 (`--set detector.half=false`) | 19.1 |
| FP16 (по умолчанию) | 31.2 |
| FP16 + чтение кадров в фоновом потоке (по умолчанию) | 32.5 |

Весь пайплайн на 4 клипах (312 с видео, без кэша; на GPU параллельно шла другая задача, цифры завышены):
до ускорения — 448 с, FP16 + один проход чтения в лёгкой стадии — 311 с (×1.44), то же с `--workers 2` — 248 с
(×1.81). FP16 верификатора ускоряет лёгкую стадию примерно на 30 %, чтение за один проход — ещё на ~8 %.

Весь набор true+false (34 клипа, 3935 с видео, один процесс, RTX 2060): трекинг 1766 → 1307 с, весь пайплайн
2066 → 1647 с (×2.4 быстрее реального времени). Медиана фона для замера света теперь считается на torch (на GPU — в 16 раз
быстрее `np.median`, результат тот же бит в бит), а сам замер идёт в отдельном потоке, пока GPU считает позу следующего
кадра. Остальное время трекинга — инференс позы (17.8 из 21 мс на кадр при `imgsz` 1280).

TensorRT FP16 для позы (опция, не по умолчанию): `tools/export_trt.py` собирает engine (~4 мин, пакеты — в
`requirements.txt`), включается через `--set detector.pose_model=weights/yolo11m-pose-fp16-dyn1280.engine`. Поза
22.5 → 16.9 мс на кадр, трекинг ×1.24 быстрее (на 39 тыс. кадрах; на клипе 2880×1620 — ×1.5). Но точки позы
сдвигаются, и на разметке пользователя при тех же порогах F1 0.583 против 0.627 (TP 14 против 16), поэтому по
умолчанию — PyTorch. Аппаратное декодирование (`CAP_PROP_HW_ACCELERATION`, D3D11) медленнее программного
(1080p: 5.4 против 2.9 мс на кадр анализа) и меняет пиксели — не используется.

FP16 немного сдвигает точки позы и уверенности верификатора: пограничные циклы и границы событий меняются.
Пороги подбирайте в том же режиме, в каком будет финальный прогон.

## Ограничения

- Ключевые точки лица на людях ниже ~100px шумят → пропуски в дальней зоне.
- Питьё и еда дают тот же жест; защита — верификатор предметов и правило двух циклов.
- Чупа-чупс: палочку в паузе детектор принимает за сигарету. Поэтому конфету (`lollipop`) ищем у кисти и рта по всему
  треку, а не только в паузах (`verifier.track_negative_*`). Это работает на крупном плане; при росте человека ~100 px
  конфета занимает пару пикселей и не видна.
- Муляж сигареты на CCTV почти не виден, поэтому основной сигнал — повторяющийся жест.
- Вспышка зажигалки видна, только когда пламя засвечивает лицо и кисти (темно, крупный план). Маленький огонёк
  днём — несколько пикселей, его не находят ни яркость, ни YOLO-World (классы `lighter`/`flame` проверены).
- Выдох пара замеряется, только пока человек стоит и зону у рта не закрывают соседи: фон за идущим человеком
  другой. Порог `vapor.min_net` подобран по нескольким выдохам в своих роликах — уточнять на эталоне. На муляжах
  пара нет, поэтому он только повышает уверенность и не обязателен.
- Касание лица, почёсывание носа, поправление маски и питьё по позе не отличить от затяжки: классификатор по 20
  признакам позы на размеченных циклах дал AUC 0.54–0.64. Поэтому у каждого валидного цикла CLIP ViT-L/14@336
  (`smokedet/appearance.py`, без дообучения) сравнивает кропы «рот + кисть» в паузе с описаниями «курит» и
  «пьёт / трогает лицо / говорит по телефону…»; цикл с оценкой ниже `appearance.min_score` без прямого признака
  отбрасывается (`reject_reason=appearance:<оценка>`). Высокая оценка работает и в обратную сторону: от
  `appearance.direct_score` цикл получает `look` — прямой признак (1 цикл + `look` = эпизод при
  `episode.appearance_as_direct`), а цикл, который верификатор отбросил за предмет из `rescue_objects` (YOLO-World
  принимает кисть с сигаретой за бутылку или стакан) или поиск циклов — только по причинам из `rescue_reasons`,
  от `rescue_score` снова валиден (`rescued_from`). На размеченных кандидатных циклах AUC 0.88, внутри клипа
  0.86. Дообучать на своих клипах нельзя: у многих камер все циклы одного класса, и модель запоминает камеру.
  Чупа-чупс CLIP принимает за сигарету — его отсекает верификатор по треку.
- Обработка офлайн: границы события уточняются по фазам подхода/отвода, поэтому задержка ≈ 0.
