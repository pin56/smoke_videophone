# Сервер на 20–30 камер: режимы GPU/CPU и регулятор нагрузки

Дата: 2026-10-09.

## Задача

Сервер AMD EPYC + NVIDIA L40S обслуживает 20–30 стационарных камер. Нужны два режима — с GPU (модели на L40S,
декодирование на CPU) и без GPU (только EPYC, OpenVINO) — и динамическое регулирование: максимум точности, пока
успеваем в реальном времени; при перегрузке деградирует то, что меньше всего стоит точности.

Требование пользователя к задержке: уведомление приходит через 5–10 с после события.

Допущения: вход — живые потоки (RTSP/любой URL OpenCV) и файлы (в темпе реального времени, для тестов и эмуляции);
тревоги — лог + `alerts.jsonl`; подключение к журналу `monitor.py` — позже. Целевого железа нет: проверка — эмуляция
N камер на Ryzen 7 9800X3D (8 ядер) и RTX 2060 (6 ГБ). Регулятор опирается на измеренное отставание, а не на числа
под железо.

Цена одной камеры сейчас (34 клипа старого набора, `runs/rt_noobj/final`, `runs/cpu/l168`): RTX 2060 без CLIP —
load 0.076 / пик 0.22; CPU с CLIP L/14@168 — 2.4 ядра в среднем / 7.6 в пике. 30 камер на CPU без деградации ≈ 70+
ядер Zen 5.

## Архитектура

Один процесс, общие модели, поток на камеру (подход «общий сервис + планировщик»). Упор одного процесса в GIL
снимается `--procs P` (`multi.py`): камеры делятся по P процессам, у каждого свои модели, Hub и регулятор, выход
процессов (`<out>/p<k>`) сливается в общий; на CPU потоки OpenVINO и исполнители делятся поровну.

```
CameraSource (поток чтения) ──кадры──▶ Camera (поток: RealtimeSession) ──запросы──▶ Hub (детектор / поза / CLIP)
        ▲                                     │ тревоги, события                         │ батчи всех камер
        └──── сетка частот ◀── Controller ◀── отставание, приоритет, загрузка ◀─────────┘
```

Модули (`smokedet/serve/`):

- `source.py` — `CameraSource`: поток чтения камеры. Все кадры декодируются (`grab`), в очередь попадают кадры
  плотной сетки (базовая `dense_fps`) и сетки детектора (текущая `sparse_fps` камеры) с меткой `arrival` (время
  прихода, wall). Файл — в темпе pts (`arrival = wall0 + t − t0`), RTSP — время `grab`. Обрыв RTSP — переподключение
  с паузой 1, 2, 5, 10 с; новый сегмент (новая сессия). Декодер FFmpeg — 1 поток на камеру
  (`OPENCV_FFMPEG_CAPTURE_OPTIONS=threads;1`, если не задано), иначе 30 камер × N потоков.
- `hub.py` — `BatchExecutor(fn, max_items, wait_ms, workers, key)`: вызов из потока камеры блокирует до результата;
  исполнитель берёт первый запрос, добирает запросы того же ключа не дольше `wait_ms` и не больше `max_items`,
  вызывает `fn` одним батчем и раздаёт результаты (исключение — каждому запросу). `Hub` собирает детектор, позу и
  CLIP из `RealtimeDetector` и отдаёт сессиям объект с `detect`/`pose` и кодировщик CLIP с тем же интерфейсом
  (`encoder(crops, view)`, ключ — вид). GPU: один исполнитель на модель. CPU: `serve.workers` исполнителей
  (0 — ядра / 4), OpenVINO компилируется с `THROUGHPUT` и `NUM_STREAMS` = исполнителей, infer request — свой у
  каждого потока (`OvYolo`, CLIP-IR). Учёт: занятость исполнителя (доля времени в `fn`), средний батч.
- `control.py` — `Controller`: чистая логика, без моделей и потоков (тестируется сценариями).
- `server.py` — `Server`: камеры, тревоги, журнал раз в секунду, завершение сегментов (события → строки
  predictions), эмуляция.
- `serve.py` — точка входа.

`RealtimeSession` не переписывается: она вызывает `self.m.detect`, `self.m.pose`, `encoder(...)` синхронно — поток
камеры ждёт свой батч, остальные камеры работают. Изменения в `realtime.py`:

- `PersonJob.fps` — частота плотной проверки задаётся заданию при старте (текущая `realtime.dense_fps` камеры);
  `_dense_step` и кадры из кольцевого буфера в `_start_jobs` берутся по тикеру задания; `build_signal` — по
  `job.fps`. Задания со старой частотой доживают с ней. `record()/replay_job` хранят `fps` (старый кэш — без поля,
  берётся `realtime.dense_fps`). При одной частоте поведение прежнее (тест эквивалентности).
- `session_result(ses, meta, stream_stats, wall, cpu) -> RtRun` вынесен из `RealtimeDetector.run`: сервер собирает
  итог сегмента так же.
- Потокобезопасность OpenVINO: infer request на поток (`threading.local`).

## Задержка

Сигнал регулятора — отставание камеры `lag` = now − `arrival` самого старого необработанного кадра. Тревога ≈ `lag` +
задержка правила (~3 с от конца цикла сейчас). Цель `lag` ≤ `serve.lag_high` 2 с (тревога ~5 с), аварийный потолок
`serve.lag_max` 6 с (тревога ≤ 10 с): дальше камера пропускает кадры плотной сетки (кадры детектора — никогда), пока
`lag` не станет < `lag_high`; пропуски — `dropped_dense` в журнале. Задержка тревоги в журнале — wall:
`lag в момент тревоги + (t − end)`.

## Регулятор

Состояние — одно целое «давление» `G` ∈ [−1, K + 3], K — число ступеней. Тик `serve.tick` 1 с:

- `lag` = максимум по камерам; `util` = максимум занятости исполнителей hub (на CPU ещё процессорное время процесса /
  число ядер).
- `lag > lag_high` → `G += 1` (`lag > 2·lag_high` → `+2`), спокойствие сбрасывается.
- `lag < lag_low` (0.5 с) и `util < util_low` (0.85) непрерывно `calm_hold` (10 с) → `G −= 1`; переход 0 → −1
  (буст) — только при `util < util_boost` (0.6).
- Иначе спокойствие сбрасывается.

Ступень камеры: `G < 0` → −1 (буст); иначе `clamp(G − приоритет, 0, K)`. Приоритет: 3 — у камеры действующая
тревога; 2 — идёт плотная проверка; 1 — люди видны в последние 10 с; 0 — пусто. Пустые камеры деградируют
первыми, камеры с курильщиком — последними.

Ступени — переопределения `realtime.*` из конфига (`serve.boost` — список, `serve.ladder` — список строк
«k=v,k=v», накопительно). Смена ступени: поля из объединения ключей всех ступеней возвращаются к базе профиля,
затем применяются ступени 1..L (или буст). Разрешены только ключи, которые сессия читает на лету:
`realtime.{skip_confirmed, dense_fps, max_jobs, sparse_fps, fill_budget, trigger_dist, alert_hold}`.

Ступени по умолчанию (порядок — по замеру цены, раздел «Проверка»):

| ступень | переопределение | что теряем |
|---|---|---|
| буст (−1) | `fill_budget=true` | — (тратим запас на людей без срабатывания) |
| 1 (только GPU; в CPU — база) | `skip_confirmed=true` | CLIP новых циклов подтверждённого события |
| 1 | `max_jobs=4` | одновременные плотные проверки на камеру |
| 2 | `dense_fps=2.5` | точность фаз цикла |
| 3 | `sparse_fps=0.5` | короткие подъёмы руки |
| 4 | `appearance.max_frames=4` | затяжки долгого курения (студенты 152 → 94 из 302) |

Замер (README, «Сервер на много камер»): max_jobs почти бесплатна, max_frames дешёва по F1 на старом наборе, но
теряет треть затяжек на студентах — последняя.

## Режимы

Профили — YAML поверх умолчаний (`load_rt_config`), выбираются `--mode`:

- `configs/serve_gpu.yaml` — CUDA, fp32 (FP16 сдвигает точки позы, пороги подобраны в fp32), поза
  `yolo11m-pose.pt`, детектор `yolo11n.pt`, CLIP L/14@168, правило и пороги CLIP как в профиле CPU.
- `configs/serve_cpu.yaml` — профиль README «На CPU»: OpenVINO det/pose, CLIP L/14@168 IR, `skip_confirmed`,
  два вида кропа, `frame_agg` max, `appearance.min_score` 3.5.

Секция `serve` в `config.py`/`default.yaml`: `tick`, `lag_low`, `lag_high`, `lag_max`, `calm_hold`, `util_low`,
`util_boost`, `people_hold`, `boost`, `ladder`, `workers` (0 — авто), `batch_wait_ms`, `max_batch`, `queue_sec`,
`reconnect`, `decode_threads`.

## Запуск и выход

```bash
python serve.py --cameras cams.csv --mode gpu --out runs/serve            # cams.csv: camera_id,url[,roi]
python serve.py --emulate 12 --inputs runs/rt/all.csv --mode cpu --out runs/serve/e12   # эмуляция 12 камер
```

Эмуляция: клипы раздаются камерам по длительности (самые длинные — первыми, каждой камере — в наименее занятую),
каждая камера играет свои клипы в темпе реального времени; кончились — повторяет их «наполнителем» (без выхода),
пока не закончат все. Выход совместим с `tools/eval_markup.py`: `predictions.csv/json`, `processing_log.csv`,
`debug/`; плюс `alerts.jsonl` (камера, клип, wall, задержка), `serve_log.csv` (тик: `G`, ступени, `lag` средний и
максимум, `util`, пропуски, тревоги), `serve_summary.json` (перцентили задержки, доля времени по ступеням).

Живой режим: сегменты (до обрыва/остановки) пишутся так же; Ctrl+C — сессии завершаются, итоги дописываются.

## Ошибки

- Обрыв потока: камера `offline`, сегмент закрывается (`finish`), переподключение по `serve.reconnect`; остальные
  камеры не затронуты.
- Исключение в модели: получают все запросы батча; камера закрывает сегмент, пишет ошибку и продолжает со
  следующего кадра новым сегментом.
- Исключение в потоке камеры не роняет сервер.

## Проверка

1. Unit: регулятор (рост давления при отставании, спад после спокойствия, буст только при запасе, приоритеты),
   `BatchExecutor` (батч из нескольких потоков, ключи, исключения), `PersonJob.fps` (при одной частоте — прежние
   отсчёты; при 3 из 5 — каждый второй/третий кадр), источник (темп, пропуски, `arrival`).
2. Цена ступеней: `run_rt.py` с каждой ступенью отдельно на старом наборе (rasmetka_gt) и студентах (students_gt):
   F1, true с TP, затяжки, время, FP в false. Порядок ступеней — от дешёвых.
3. Эквивалентность: эмуляция без перегрузки (ступень 0) даёт те же метрики, что `run_rt.py` (± пограничные события
   из-за состава батчей fp16/bf16).
4. Нагрузка: эмуляция N камер (CPU-режим на 9800X3D, GPU-режим на RTX 2060), N растёт: задержка тревоги p50/p95/max,
   доля времени по ступеням, пропуски, F1/затяжки под нагрузкой. Максимальное N с p95 ≤ 10 с.
5. Не проверяется здесь: EPYC, L40S, настоящие RTSP-камеры — на сервере нужен один прогон эмуляции.
